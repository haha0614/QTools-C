# P5.94 · 「刷新进入人物页时卡片背景先被拉高再恢复正常」实测报告

被测页面：`/media/persons`（QTools-C，vite dev 现编真 SFC，人物数据走真实后端 127.0.0.1:8080）
仪器：`devtools/p594-ui/frames.mjs` + `probe.js`（document-start 注入 rAF 逐帧探针，CDP 采网络）

## 1. 真因（两条，都实测到了）

### 真因 A：卡片高度是「内容撑出来的」，首帧 84 → 数据到达后 103.7

```
.pw-card  min-height: 84px;  height: 100%;   （grid-auto-rows: 1fr）
```

首屏第一帧只有姓名（`.pw-body` 22.4px）→ 84（min-height）；
随后 `GET /api/index`（counts）与 `GET /api/person/<id>`（chips / recent）到达，
`.pw-body` 变 81.7 → 卡片 **在同一张卡上** 从 84 跳到 103.7。

修前逐帧证据（1600×1000，light，第 2 次刷新，第 0 张卡）：

| t(ms) | .pw-card | .pw-bg | .pw-bg-card | URL w/h | 自然尺寸 | stretch | stage |
|---|---|---|---|---|---|---|---|
| 146.4 | **84** | null | null | 0/0 | 0×0 | 1 | - |
| 168.1 | **84** | 82 | null | 0/0 | 0×0 | 1 | - |
| 218.3 | **103.7** | 101.7 | 101.7 | 240/58 | 240×58 | **0.792** | preview |
| 526.8 | 103.7 | 101.7 | 101.7 | 332/102 | 332×102 | 1.007 | full |

稳定后内容审计（同一轮）：`maxNeed=101.7`（body 81.7 + padding 20）、卡片 103.7（+2 border）；
`count=13` 张卡全部 103.7 —— 也就是说 84 只是「数据还没到」时的假高度。

### 真因 B：`object-fit: fill` 把「按旧高度烘的图」硬拉进新盒子

`.pw-bg-card { object-fit: fill }`（原 1876 行）的语义是「不管原图宽高比，硬拉满盒子」。
低清图是**两段式的第一张**，它是按测量那一刻的盒子（84 高）烘的：`w=240&h=58`（比例 4.14）；
数据到达后盒子变成 328×101.7（比例 3.23）→ 图片被纵向拉伸 **1/0.792 = 1.26 倍**
= 用户眼里的「背景被拉高」。等正式图 `w=332&h=102`（与盒子同比例）回来，拉伸消失
= 「恢复正常」。这段窗口在实测里是 **218ms → 527ms（309ms）**，正好是一次「拉高再回弹」。

两条是**竞速关系**：若低清图来得晚（盒子已经长到 103.7 才量），就没有拉伸，只剩 A 的卡高跳动
（修前 1600 light 第 1 次刷新：`Δcard=19.7` 而 `Δbg=0`、stretch 恒 1.01）。
两个现象因此都表现为「刷新那一刻不对，然后就好了」。

## 2. 修法（只动 `src/views/media/PersonsPage.vue` 的 CSS，共 3 处）

| # | 位置 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `.pw-card`（1800 行） | `min-height: 84px` → **`min-height: 104px`** | 104 = 满内容 81.7（22.4 姓名 + 15.5 counts + 18 chips + 16.8 recent + 3×3 gap）+ 20 padding + 2 border。所有卡 ≥104 且内容 ≤104 → 卡片高度**与数据无关**，首帧就是终值；`.pw-bg` clientHeight 恒 102 → URL 恒 `w=332&h=102`（与修前稳定态**同一个 URL**，缓存不重建） |
| 2 | `.pw-bg-card`（1891 行） | `object-fit: fill` → **`object-fit: cover; object-position: center`** | 比例一致时两种取值渲染逐像素相同；比例不一致时只裁切、不拉伸 —— 从此不存在「被拉高」这种可能（窗口 resize、两段式、任何盒子变化都一样） |
| 3 | `.pw-bg`（1844 行） | `transition: transform .12s ease` → **`transition: none`**，缓动搬进 `:hover / :focus-visible` 规则（1986 行） | 背景层静止态**没有**任何 height / transform 过渡可跑；hover 缩放（pointer 驱动，加载时永不成立）仍然是 0.12s 缓动 |

首帧到图片就绪之间：容器高度由 CSS 决定（不再由内容撑开），底色是已有的「拾色底」
（`.pw-card.has-tone` 的 `--pw-tone`），所以只有图片内容延迟出现，没有几何变化。
两段式本身没改：低清 `w=240&h=74` 与正式 `w=332&h=102` 比例一致（`cardBgPreview` 等比缩），换图只有清晰度变化。

## 8. 已知限制

1. 桌面档的稳定高度从 103.7 变成 104（+0.3px），375 档从「内容撑出来的 101」变成 104（+3px）：
   代价是换来「高度与数据无关」，375 单列上肉眼不可见。`min-height: 104px` 是按当前字号/行高
   算出来的常量（14px 字号、1.35–1.5 行高）。
   浏览器**最小字号**设置调大后内容可能超过 104 → 又变成内容撑高（那时 104 只是下限）。
   页面所有字号都是 px，页面缩放不影响这个算式（缩放不改 CSS px 口径）。
2. 盒子在**低清图烘好之后**又变化（比如载入中途拉窗口）：低清图不会重烘（`cardBgPreview` 只定一次，
   为的是守住「每卡 ≤2 请求」），这期间靠 `object-fit: cover` 裁切，构图会偏一点点，
   正式图（新尺寸）在 100ms 静默 + 渲染延迟内替换。
3. `.pw-bg` 的 hover 缩放现在「移入缓动、移出瞬时」（缓动只写在 `:hover` 规则里）。
   这是「静止态不许有 transform 过渡」的代价，视觉上是 3% 缩放在指针移出时立刻归位。
4. 本轮只在真实后端（127.0.0.1:8080，13 位人物）上跑；p594 的断言依赖「有头像来源的人物 ≥ 6」。

## 9. 环境备注：后端在实测末尾掉了媒体端点（与本改动无关）

验收主体（§3–§6、§7 的 p590/p593/p588/p552）都是在后端健康时跑的：
`GET /api/media/person/<id>/card-bg` 200，13 张卡各 2 个请求（240 占位 + 332 正式），全帧可见 full 阶段。

之后同一台后端（127.0.0.1:8080）**媒体类端点整体变 404**（`/card-bg` 404、`/api/media/thumb/...` 也 404，
而 `/api/media/persons` 仍 200）—— 属于环境状态变化，不是本次改动引起的。
在这种状态下页面走「card-bg 失败 → 三层兜底 → 连原图也 404 → 无背景层」的老错误路径
（`.pw-bg` / `.pw-bg-card` 计数在 0…12 之间抖动，那是 `cardBgFailed` / `bgSrcOf` 的 v-if 逻辑，纯 JS，CSS 改不到）。

顺手在 404 状态下复测了一次高度（`out/after-fallback404`，1600 light × 2）：
**`.pw-card` 仍然恒 104、Δ=0（9/9 → 6/6 PASS）** —— 说明本修法不依赖服务端图，兜底路径同样不跳。
要重跑完整矩阵，等后端媒体端点恢复即可：`node devtools/p594-ui/frames.mjs after --runs=3 --trace`。
